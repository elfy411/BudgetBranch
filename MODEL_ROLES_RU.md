# BudgetBranch — модели и запуск агентов (v2)

**Решение владельца:** используются максимальные доступные уровни рассуждения **Max для всех ролей**. Оптимизировать расход лимитов не нужно. Выбор модели определяется качеством работы и независимостью проверки.

## Точное распределение

| Роль | Модель (как выбирать в интерфейсе) | Effort | Основной результат |
|---|---|---|---|
| Главный Integrator / Tech Lead | **Astra 6** | **Max** | Архитектура, план, ревью, интеграция, финальная сборка |
| Contract Engineer | **Astra 6** | **Max** | NEAR Rust smart contract + async выплаты + unit/Sandbox evidence |
| Independent Security QA | **Astra 6** | **Max** | Отдельная проверка инвариантов и adversarial тестирование |
| SDK & Agents | **Sol 6.1** | **Max** | TypeScript SDK, scripted agents, примеры |
| Frontend | **Sol 6.1** | **Max** | React UI на фактическом состоянии контракта |
| Integration Tests & CI | **Sol 6.1** | **Max** | E2E, воспроизводимая сборка, минимальный CI |

В контекстах OpenAI API идентификаторы моделей: `gpt-6-astra`, `gpt-6.1-sol`. **`max` — это значение effort, а не суффикс имени модели.** В Codex UI/CLI надо выбирать реально доступные варианты; не переносить синтаксис API в `config.toml`, если клиент его не документирует.

## Принцип запуска

1. Владелец запускает **Integrator: Astra 6 Max**.
2. Integrator делает M0, публикует `SPEC.md`, получает одобрение **G0**.
3. Затем стартует **Contract: Astra 6 Max**, **SDK: Sol 6.1 Max**, **Frontend: Sol 6.1 Max** в изолированных worktrees/ветках.
4. **Security QA: Astra 6 Max** начинает read-only threat model по SPEC, затем проверяет контракт и интегрированную сборку; не программирует собственные исправления вместо автора.
5. **Integration Tests/CI: Sol 6.1 Max** пишет изолированные тесты под утверждённый ABI и помогает с чистым запуском.
6. Integrator принимает работу только по diff и повторно запущенным тестам. Одобрения владельца на G1/G2/G3 обязательны.

## Важное ограничение окружения

- **Не во всех режимах Codex главный агент может управлять моделью каждого запущенного субагента.** Надпись в промпте не гарантирует выбор нужной модели.
- Если запуск субагентов позволяет явно выставить модель и effort: использовать именно матрицу выше и записать факт выбора.
- Если субагенты наследуют модель интегратора или невозможно проверить их настройки: **открыть отдельные Codex-сессии** на нужных моделях и effort с промптами из `PROMPTS_WORKERS_RU.md`; каждая в отдельном worktree. Integrator получает ветки и проверяет их.
- Если отдельные сессии невозможны, нельзя утверждать, что достигнута требуемая модельная конфигурация; сообщить владельцу и выбрать доступный режим явно.
- Не запускать Astra QA с общим контекстом Contract Engineer, где он лишь подтверждает собственные допущения. Независимый контекст и отдельное ревью важнее совпадающих названий моделей.

## Оптимальный параллелизм

Одновременно: Contract + SDK + Frontend, пока Integrator координирует. QA работает без конфликтующих правок. Integration Tests может стартовать после freeze SPEC, но не должна параллельно менять `contracts/**`, `sdk/**`, `web/**`.

**Max может выполняться дольше.** Прогресс измерять не числом запущенных агентов, а временем до единого работающего сценария и числом проверенных инвариантов. Не создавать дополнительных агентов ради количества.

## Что каждый агент пишет в конце работы

```text
ROLE / MODEL / EFFORT (подтверждено интерфейсом или «не могу проверить»)
BRANCH / COMMIT / OWNED PATHS
DONE / NOT DONE / BLOCKED
EXACT COMMANDS + PASS/FAIL RESULTS
SANDBOX vs TESTNET vs MOCK
KNOWN RISKS + WHAT THE INTEGRATOR MUST REVIEW
```
