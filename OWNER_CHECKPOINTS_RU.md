# BudgetBranch — контрольные точки владельца (v2)

Роль владельца — принимать существенные решения и проверять настоящую демонстрацию, а не ежедневно распределять мелкие задачи. Интегратор: **Astra 6 Max**; Contract и Security QA также **Astra 6 Max**; SDK, UI, Integration Tests — **Sol 6.1 Max**.

## G0 — архитектура: посмотреть ДО параллельной реализации

Попросить одну страницу и `SPEC.md`. Проверить:

- [ ] Контракт не выдаёт физически деньги при делегировании, а **резервирует** их в одном обеспеченном бюджете.
- [ ] Согласована формула `available + child_reserved + pending + spent + returned` без двойного счёта между предками/потомками.
- [ ] Каждый новый ребёнок получает **не более узкие** recipient allowlist, срок, сумму и глубину.
- [ ] Действительная on-chain caller authorization (не доверие к переданному в JSON `agent_id`).
- [ ] Статусы pending/succeeded/failed, callback, revoke и возврат разъяснены.
- [ ] Контракт, SDK, UI и E2E используют **единый** замороженный ABI.
- [ ] Integrator предъявил матрицу реальных моделей **Astra/Astra/Astra/Sol/Sol/Sol, все Max**, либо честно объяснил невозможность проверить и предложил отдельные потоки.
- [ ] Указаны branch/worktree и ownership путей; никто не редактирует одни файлы параллельно.

**Решение:** `G0 APPROVED` или `G0 CHANGES REQUIRED: ...`.

## G1 — контракт и безопасность: показывать реальный код + логи

Попросить runbook с командами, статусом, commit, логи Sandbox и независимый отчёт **Astra Security QA**. Проверить:

- [ ] Владелец выделил 10 test NEAR; A получает 6, B получает 4.
- [ ] A выделяет 4 ребёнку; второй grant ещё 4 отклоняется прямым вызовом контракта.
- [ ] Запрещённый получатель, расширение прав и посторонний caller отклоняются.
- [ ] Вызов из отозванной ветки отклоняется, соседняя ветка работает.
- [ ] Дублирующая операция не приводит к повторной выплате.
- [ ] Демонстрационный receiver принимает и намеренно отклоняет вызов; проверено реальное `pending/success/failure`.
- [ ] После callback нет ложного списания/двойного возврата резерва; callback нельзя вызвать извне.
- [ ] QA отдельно проверил хотя бы один риск, который не входил в happy-path разработчика; все critical/high дефекты закрыты либо выпуск заблокирован.
- [ ] Используются тестовые средства, секретов в git нет; тесты отделены от моков.

**Решение:** `G1 APPROVED` / `G1 CHANGES REQUIRED: ...`.

## G2 — полный рабочий сценарий на Mac

Из чистого checkout (или изолированной копии) по README:

1. Запустить unit + Sandbox тесты. Посмотреть количество PASS/FAIL, версии и реальные exit codes.
2. Открыть UI и проверить, что дерево отражает **состояние контракта**, а не только frontend fixture.
3. Выполнить grant/delegate/spend/revoke; увидеть реальные ошибки перерасхода и неверного recipient.
4. Проверить различение `MOCK`, `SANDBOX`, `TESTNET`; не принимать выдуманные tx hashes.
5. Проверить, что scripted агенты обозначены `scripted`, а live LLM — только если он реально включён.
6. Проверить английский README и запуск без скрытой локальной конфигурации/платного API.
7. Получить от Astra Security QA финальную отметку о неустранённых рисках и отдельную проверку собранной версии.

Только после этого разрешить merge `integration → main`: `G2 APPROVED TO MERGE`.

## G3 — разрешение на публикацию / заявку

- [ ] На `main` именно проверенная версия, репозиторий можно открыть публично; история git проверена на секреты.
- [ ] README корректен: что сделано, что не сделано, Testnet/Sandbox, ссылки, ограничения и внешние заимствования.
- [ ] Видео показывает **работающий результат**, не UI-заготовку; для локального демо видео обязательно.
- [ ] Текст X честный, с @NEARProtocol и #NEARHackathon, без обещаний «unhackable».
- [ ] Ссылки на публичный GitHub и пост в X доступны без логина; заявка заполнена по официальным правилам.
- [ ] Для потенциального приза указан **личный NEAR Mainnet-адрес** (не Testnet), без передачи приватного ключа.
- [ ] До дедлайна 2026-11-14 23:59 UTC осталось достаточно времени отправить форму; не откладывать на последнюю минуту.

**Решение:** `G3 APPROVED TO PUBLISH` отдельно от `APPROVED TO SUBMIT`. Публикация и отправка выполняются только после соответствующего явного решения владельца.

## Если дедлайн близко

Сокращать: AI-live, анимации, дополнительный дизайн, сайт/VPS/домен, дополнительные треки. Не сокращать: реальные финансовые ограничения, негативные тесты, репродуцируемый запуск, безопасность ключей и честность описания.

При блокирующей ошибке финансов нельзя называть такую версию безопасной или показывать поддельный успешный платёж. Зафиксировать границу реализованного, исправить или убрать соответствующее обещание из заявки.
